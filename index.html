What cognitive debt costs

Less time decoding code. More time building with it.

Much of the speed AI adds to writing code is lost after it's written. Every engineer pays it back in hours spent reviewing AI-generated code and untangling the production incidents it causes.

Review: 3.2 h/week before AI (Sadowski et al., Google, 2018) and +91% with heavy AI use (Faros AI, 2025); the striped part is the upper range, if all of that is hands-on time. Rework before AI: 3.8 h/week fixing bad code (Stripe, 2018); fixing AI-assisted code: 139+ hours a year (ActiveState, 2026), some of which may replace rework human-written code would have needed. Code per engineer: 2.4–3.5× lines changed per developer over 2025–26 (Greptile, 2026; Cursor), counted as lines, not value. Review coverage: PRs with any human review fell from 89% to 68%, and with a human comment from 39% to 21%, at one company of several hundred engineers using Claude Code (arXiv 2607.01904, 2026). Merged without full understanding: TestMu AI, 2026. The two costs may overlap in part.

Where cognitive debt builds up, from one turn to the whole codebase

Each turn, each change, each pull request, the whole codebase.

Cognitive debt builds up wherever code arrives faster than you take it in. Each tool closes the gap where it usually opens. One example runs through all four: making a CSV export resume after a crash. The After pictures work like the real pages, so click their cards, groups and tabs.

    Change Walkthrough draws the edit as a tree of groups (which ones deliver the change, which ones make them possible), then walk through each group's steps alongside its diff.

  3. Each pull request

    DebtReviewers spend most of their time working out what the diff is for before they can judge it.

    What is this PR for, and how does each part serve it?

    PR Briefing builds the mental model before you read a line of code: the objective, background, flow diagrams of how the changed code runs, then the diff in explained groups.

  4. The whole repo

    DebtThe codebase outgrows anyone's picture of it, and the reasons behind each change get lost.

    Which code is responsible for which product behavior, and how and why was it built that way?

    Codebase Atlas explains the product as its users experience it, map that behavior to the parts of the code responsible for it, and link every Change Walkthrough that touched those parts. New hires step through those changes to see how it was built, and on-call engineers go back to them to see why.

How Change Walkthrough fixes it

  • The breakdown first. A tree drawn sideways shows the whole change, the groups that deliver it, and the groups that make those possible.
  • Virtual diffs. Each group of edits has its own objective, the background you need, the steps it adds, and how it serves the larger goal of the change.

How Codebase Atlas fixes it

  • How it works explains the product, the way its user experiences it.
  • How the code works explains the structure and parts of the codebase: what each part owns and how one run flows through it.
  • How it was built lists the history of changes, each with why and how it was made at the time it was made.
  • It keeps itself current. The docs update after every turn that changes files.

Principles

The rules it runs by.

The rules every tool follows.

Pictures before prose

Flows, diagrams, before-and-after tables and breakdown trees show the big picture at a glance, so you understand how things fit before reading any detail.

What if an explanation is wrong?

It can be, so it stays checkable. Each step of a Change Walkthrough is pinned to a real hunk and shown with its diff, a symbol not found in that hunk is dropped, every hunk appears exactly once, and a turn's sources are its real tool calls.

Pages stay in your repo

Pages are plain HTML files in your repo, with no InTheLoop server or account. Your code and conversation reach the model only through Claude Code. The one thing written elsewhere is a short summary block in the PR description.

Install

One command per repo.

  • Claude Code, logged in. InTheLoop calls claude -p with your login.
  • Python 3.10+, standard library only. No other packages to install.
  • git, strongly recommended; required for pull request pages.
  • GitHub CLI, logged in with gh auth login, for pull request pages.
# install InTheLoop into a repo
$ intheloop install /path/to/your/repo
# then run /hooks in Claude Code to load the hooks

Every page is a plain HTML file written inside your repo, and it updates as you work.
